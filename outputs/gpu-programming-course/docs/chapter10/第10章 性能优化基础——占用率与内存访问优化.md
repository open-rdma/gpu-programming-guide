## 10.1 整体性能优化策略

NVIDIA CUDA Programming Guide 将性能优化的基本策略归纳为四条（新版为四条，旧版为三条+一条）：

1. <strong>最大化并行执行以获得最高的利用率</strong>（Maximize Utilization）
2. <strong>优化内存使用以获得最高的内存吞吐量</strong>（Maximize Memory Throughput）
3. <strong>优化指令使用以获得最高的指令吞吐量</strong>（Maximize Instruction Throughput）
4. <strong>最小化内存颠簸</strong>（Minimize Memory Thrashing）

这三条（或四条）策略共同构成了性能优化的"三大支柱"。重要的是，对于应用中的不同部分，最有价值的优化策略是不同的。例如，优化一个受内存访问限制的内核的指令使用，不会带来任何显著的性能提升。优化工作应该始终以测量和监控性能限制因素为导向——例如使用 CUDA Profiler 或 Nsight Compute。

将特定内核的浮点运算吞吐量或内存吞吐量与设备的理论峰值进行比较，可以指示该内核还有多少改进空间。

### 10.1.1 Roofline 模型简介

在开始优化之前，理解你的内核受什么因素限制至关重要。Roofline 模型是一个强大的可视化工具：

- <strong>计算受限（Compute-bound）</strong>：内核的计算强度（Arithmetic Intensity，FLOP/Byte）高，性能受限于 GPU 的计算能力
- <strong>内存受限（Memory-bound）</strong>：内核的计算强度低，性能受限于内存带宽

一个典型的向量加法（`C = A + B`）是内存受限的——每个浮点数需要2次读和1次写，只做1次加法。而矩阵乘法天然具有更高的计算强度，更容易达到计算受限。

> **小贴士**：算术强度 = 浮点运算次数 / 内存访问字节数。这是判断内核属于哪种瓶颈的关键指标。

## 10.2 最大化利用率——占用率优化

为了最大化利用率，应用程序应该以暴露尽可能多的并行性并将这种并行性高效映射到系统的各个组件的方式构建，以便使它们大部分时间保持忙碌。

### 10.2.1 应用级（Application Level）并行

在高层面上，应用程序应该通过使用异步函数调用和流（Stream）来最大化主机（Host）、设备（Device）以及连接主机的总线之间的并行执行。它将最适合的工作分配给最适合的处理器：串行工作负载交给主机，并行工作负载交给设备。

对于并行工作负载，在算法中因线程需要同步以共享数据而破坏并行性的点，有两种情况：

- <strong>线程属于同一个 block</strong>：使用 `__syncthreads()` 并通过共享内存在同一个内核调用中共享数据
- <strong>线程属于不同的 block</strong>：必须通过全局内存使用两次独立的内核调用来共享数据（一次写入，一次读取）

第二种情况效率较低，因为它增加了额外内核调用和全局内存流量的开销。应该尽可能将需要线程间通信的计算映射到同一个线程块内完成。

### 10.2.2 设备级（Device Level）并行

在较低层面，应用程序应最大化设备上各多处理器（Multiprocessor，SM）之间的并行执行。多个内核可以在设备上并发执行，因此通过使用流让足够多的内核并发执行，也可以实现最大利用率。

### 10.2.3 多处理器级（Multiprocessor Level）——占用率

在更低层面，应用程序应该最大化多处理器内部各功能单元之间的并行执行。

GPU 多处理器主要依赖<strong>线程级并行（Thread-Level Parallelism）</strong>来最大化其功能单元的利用率。因此，利用率直接与常驻 warp 的数量相关。

在每个指令发射时刻，warp 调度器选择一个准备好执行的指令。这个指令可以是同一 warp 的另一条独立指令（利用<strong>指令级并行</strong>），或者更常见的是另一个 warp 的指令（利用<strong>线程级并行</strong>）。

一个 warp 准备好执行下一条指令所需的时钟周期数称为<strong>延迟（Latency）</strong>。当所有 warp 调度器在延迟期间每个时钟周期始终都有某个 warp 的指令可供发射时——即延迟被完全"隐藏"时——就实现了充分利用。

隐藏 L 个时钟周期的延迟所需的指令数量取决于这些指令的吞吐量。假设指令以最大吞吐量执行：

- 对于 Compute Capability 5.x、6.1、6.2、7.x 和 8.x 的设备，需要 <strong>4L</strong> 条指令（一个多处理器每个时钟周期为4个 warp 各发射1条指令）
- 对于 Compute Capability 6.0 的设备，需要 <strong>2L</strong> 条指令
- 对于 Compute Capability 3.x 的设备，需要 <strong>8L</strong> 条指令

<strong>延迟隐藏的核心思想</strong>是：当某些 warp 在等待内存访问结果时（延迟可能达到数百个时钟周期），其他 warp 可以继续执行。只要有足够多的活跃 warp，GPU 就能始终保持忙碌。

> **形象比喻**：想象一个餐馆厨房。如果只有一个厨师，当他等待水烧开时，整个厨房就闲置了。但如果有8个厨师，当其中1个在等水烧开时，另外7个可以继续炒菜、切菜、装盘——这就是延迟隐藏。

warp 不能执行下一条指令的最常见原因是<strong>指令的输入操作数尚未就绪</strong>：

- 如果所有输入操作数都在寄存器中，延迟由寄存器依赖性引起。在 Compute Capability 7.x 设备上，大多数算术指令的执行时间通常为4个时钟周期，这意味着每个多处理器需要 <strong>16个活跃 warp</strong>（4个周期 x 4个 warp 调度器）来隐藏算术指令延迟。
- 如果某个输入操作数位于片外内存（off-chip memory），延迟要高得多——通常为数百个时钟周期。此时需要更多 warp 来保持调度器忙碌。

<strong>算术强度（Arithmetic Intensity）</strong>是程序中不使用片外内存操作数的指令数与使用片外内存操作数的指令数之比。算术强度越低，需要更多的 warp 来隐藏内存延迟。

warp 不能执行下一条指令的另一个原因是它在等待某个内存栅栏（Memory Fence）或同步点（Synchronization Point）。同步点可能迫使多处理器空闲，因为越来越多的 warp 在等待同一 block 中的其他 warp 完成同步点之前的指令。在每个多处理器上拥有多个常驻 block 可以帮助减少这种情况下的空闲，因为不同 block 的 warp 不需要在同步点互相等待。

### 10.2.4 占用率的定义与计算

<strong>占用率（Occupancy）</strong>定义为：

```
占用率 = 每个多处理器的活跃 warp 数 / 每个多处理器的最大 warp 数
```

影响占用率的关键因素是内核的资源使用：

1. <strong>寄存器使用量</strong>：每个线程使用的寄存器数量
2. <strong>共享内存使用量</strong>：每个 block 使用的共享内存字节数
3. <strong>线程块大小</strong>：每个 block 的线程数

这些资源的组合决定了每个 SM 上可以常驻多少个 warp。

#### 寄存器使用对占用率的影响

寄存器数量对常驻 warp 数有显著影响。以一个 Compute Capability 6.x 设备为例：假设内核使用64个寄存器，每个 block 有512个线程且几乎不需要共享内存，那么两个 block（即32个 warp）可以常驻在多处理器上，因为它们需要 2 x 512 x 64 = 65536 个寄存器，恰好匹配多处理器上可用的寄存器数量。但如果内核多使用1个寄存器（65个），就只能常驻1个 block（16个 warp），因为两个 block 需要 2 x 512 x 65 = 66560 个寄存器，超过了多处理器的寄存器数量。

> **关键启示**：寄存器使用量的微小差异可能导致占用率的剧烈变化。编译器会努力在保持寄存器溢出（Register Spilling）和指令数量最小的前提下最小化寄存器使用量。

寄存器文件被组织为32位寄存器。因此，每个存储在寄存器中的变量至少需要一个32位寄存器。例如，一个 `double` 变量使用两个32位寄存器。

#### 编译器资源报告

当使用 `--ptxas-options=-v` 选项编译时，编译器会报告寄存器和共享内存的使用情况：

```bash
nvcc -arch=sm_86 --ptxas-options=-v kernel.cu -o kernel
```

输出示例：
```
ptxas info    : Used 32 registers, 4096 bytes smem, 4 bytes cmem[0]
```

### 10.2.5 占用率计算器（Occupancy Calculator）

CUDA 提供了多个 API 函数来帮助程序员根据寄存器和共享内存需求选择线程块大小。

#### 预测占用率

`cudaOccupancyMaxActiveBlocksPerMultiprocessor` 可以根据内核的块大小和共享内存使用量提供占用率预测。这个函数以每个多处理器的并发线程块数报告占用率。可以将其转换为其他度量：乘以每个 block 的 warp 数得到每个多处理器的并发 warp 数，再除以每个多处理器的最大 warp 数得到百分比形式的占用率。

```cpp
// 设备代码
__global__ void MyKernel(int *d, int *a, int *b)
{
    int idx = threadIdx.x + blockIdx.x * blockDim.x;
    d[idx] = a[idx] * b[idx];
}

// 主机代码
int main()
{
    int numBlocks;        // 以活跃 block 数表示的占用率
    int blockSize = 32;

    int device;
    cudaDeviceProp prop;
    int activeWarps;
    int maxWarps;

    cudaGetDevice(&device);
    cudaGetDeviceProperties(&prop, device);
    
    cudaOccupancyMaxActiveBlocksPerMultiprocessor(
        &numBlocks,
        MyKernel,
        blockSize,
        0);

    activeWarps = numBlocks * blockSize / prop.warpSize;
    maxWarps = prop.maxThreadsPerMultiProcessor / prop.warpSize;

    std::cout << "Occupancy: " 
              << (double)activeWarps / maxWarps * 100 
              << "%" << std::endl;
    
    return 0;
}
```

#### 自动配置内核启动参数

`cudaOccupancyMaxPotentialBlockSize` 和 `cudaOccupancyMaxPotentialBlockSizeVariableSMem` 可以启发式地计算实现最大多处理器级占用率的执行配置。

```cpp
int launchMyKernel(int *array, int arrayCount)
{
    int blockSize;      // 启动配置器返回的块大小
    int minGridSize;    // 实现全设备最大占用率所需的最小网格大小
    int gridSize;       // 基于输入大小的实际网格大小

    cudaOccupancyMaxPotentialBlockSize(
        &minGridSize,
        &blockSize,
        (void*)MyKernel,
        0,
        arrayCount);

    // 根据数组大小向上取整
    gridSize = (arrayCount + blockSize - 1) / blockSize;

    MyKernel<<<gridSize, blockSize>>>(array, arrayCount);
    cudaDeviceSynchronize();
    return 0;
}
```

CUDA Toolkit 还在 `<CUDA_Toolkit_Path>/include/cuda_occupancy.h` 中提供了一个独立的占用率计算器。此外还提供了一个电子表格版本的占用率计算器，特别适合作为学习工具——它可视化展示了影响占用率的参数（块大小、每线程寄存器数、每线程共享内存）变化的影响。

### 10.2.6 线程块大小的选择启发式

选择线程块大小时应遵循以下原则：

1. <strong>线程块大小应该是 warp 大小（32）的倍数</strong>——避免因 warp 未填满而浪费计算资源
2. <strong>典型推荐范围：128-512 个线程/block</strong>
3. <strong>每个 block 至少要有多个 warp</strong>——这样当一些 warp 在等待同步时，其他 warp 可以继续执行
4. <strong>每个 SM 上要有多个常驻 block</strong>——来自不同 block 的 warp 不需要在 `__syncthreads()` 处互相等待
5. <strong>使用占用率 API 工具来辅助选择</strong>

<strong>实际建议</strong>：对于简单的逐元素内核，256 个线程/block 通常是好的起点。对于使用大量共享内存的内核，可能需要使用更小的块大小（如128）。

## 10.3 最大化内存吞吐量——数据传输优化

最大化整体内存吞吐量的第一步是<strong>最小化低带宽的数据传输</strong>。

这意味着最小化主机和设备之间的数据传输，因为它们的带宽远低于全局内存和设备之间的数据传输带宽。也意味着通过最大化利用片上内存（共享内存和缓存）来最小化全局内存和设备之间的数据传输。

### 10.3.1 Host-Device 数据传输优化

#### PCIe 带宽限制

主机与设备之间的数据传输通过 PCIe 总线进行。以 PCIe 3.0 x16 为例，理论带宽约为 16 GB/s，而现代 GPU 的全局内存带宽通常为数百 GB/s（如 RTX 3060 约为 360 GB/s）。这意味着 <strong>PCIe 带宽通常是系统瓶颈</strong>。

应用程序应该<strong>努力最小化主机和设备之间的数据传输</strong>。一种方法是<strong>将更多代码从主机迁移到设备</strong>，即使这意味着运行那些暴露的并行性不足以在设备上高效执行的内核。中间数据结构可以在设备内存中创建、操作和销毁，而无需被主机映射或复制到主机内存。

另外，由于每次传输都有开销，<strong>将多个小传输合并为一个大传输</strong>总是比分别进行每次传输性能更好。

#### Page-Locked（页锁定）内存

在具有前端总线（Front-Side Bus）的系统上，使用<strong>页锁定主机内存（Page-Locked Host Memory）</strong>可以实现更高的主机与设备数据传输性能。页锁定内存（也称为"固定内存"）不会被操作系统换出到磁盘，这使得 DMA（直接内存访问）控制器可以直接访问它而无需先锁定页面。

```cpp
// 普通可分页内存
float *h_data = new float[N];
cudaMemcpy(d_data, h_data, N * sizeof(float), cudaMemcpyHostToDevice);

// 页锁定内存
float *h_pinned;
cudaMallocHost(&h_pinned, N * sizeof(float));
cudaMemcpy(d_data, h_pinned, N * sizeof(float), cudaMemcpyHostToDevice);
cudaFreeHost(h_pinned);
```

<strong>注意事项</strong>：页锁定内存是稀缺资源。分配过多的页锁定内存会减少系统可用的物理内存量，可能降低整体系统性能。

#### Mapped Memory（映射内存）

当使用映射页锁定内存时，无需分配任何设备内存，也无需显式地在设备和主机内存之间复制数据。数据在每次内核访问映射内存时隐式传输。

```cpp
float *h_mapped;
cudaHostAlloc(&h_mapped, N * sizeof(float), cudaHostAllocMapped);
// 无需 cudaMalloc 和 cudaMemcpy，内核可以直接访问 h_mapped
```

为获得最大性能，这些内存访问必须像全局内存访问一样进行合并。在集成系统（Integrated System）上，设备内存和主机内存在物理上是相同的，任何主机与设备之间的复制都是多余的，此时应使用映射页锁定内存。

> **权衡**：映射内存提供了编程便利性，但如果你不精确控制访问时机，可能会在你不期望的时候触发 PCIe 传输，导致性能退化。

## 10.4 最大化内存吞吐量——设备内存访问优化

访问可寻址内存（全局、局部、共享、常量或纹理内存）的指令可能需要根据 warp 内线程间内存地址的分布而多次重复发射。地址分布越分散，吞吐量越低。

<strong>内核的内存访问吞吐量可以根据访问模式变化一个数量级</strong>。因此，内存访问优化的下一步是基于最优内存访问模式来尽可能优化地组织内存访问。这种优化对于全局内存访问特别重要，因为全局内存带宽相对于可用的片上带宽和算术指令吞吐量来说较低，所以非最优的全局内存访问通常对性能影响很大。

### 10.4.1 全局内存合并访问（Global Memory Coalescing）

这是 <strong>CUDA 性能优化中最重要的概念之一</strong>。理解并善用合并访问，有时能让你的内核性能提升数倍。

#### 内存事务（Memory Transaction）

全局内存位于设备内存（Device Memory，即显存/DRAM）中，设备内存通过 <strong>32字节、64字节或128字节的内存事务（Memory Transaction）</strong>进行访问。这些内存事务必须是自然对齐的：只有对齐到其大小的设备内存段（即首地址是其大小的倍数）才能被内存事务读取或写入。

当一个 warp 执行访问全局内存的指令时，它会根据每个线程访问的字大小和线程间内存地址的分布，将该 warp 内线程的内存访问<strong>合并（Coalesce）</strong>为一个或多个内存事务。一般来说，需要的事务越多，除了线程实际访问的字之外传输的未使用字就越多，指令吞吐量也就随之降低。

例如，如果为每个线程4字节的访问生成一个32字节的内存事务，吞吐量将除以8。

#### 合并访问的核心规则

<strong>理想情况</strong>：当 warp 中的所有32个线程访问<strong>连续的、对齐的</strong>内存地址时，整个 warp 的访问可以被合并为最少数量的内存事务。

让我们通过具体例子来理解合并访问：

```cuda
// 场景1：完美合并 - 线程访问连续的 float
// thread i 读取 array[i]
// 32个线程访问连续的128字节，可以由4个32字节事务或1个128字节事务完成
__global__ void coalesced_read(float *input, float *output) {
    int idx = threadIdx.x + blockIdx.x * blockDim.x;
    output[idx] = input[idx];  // 完美合并！
}

// 场景2：跨步访问 - 线程访问间隔的数据
// thread i 读取 array[i * stride]
// 当stride=2时，需要双倍的内存事务
__global__ void strided_read(float *input, float *output, int stride) {
    int idx = threadIdx.x + blockIdx.x * blockDim.x;
    output[idx] = input[idx * stride];  // stride>1时合并效率降低
}

// 场景3：随机访问 - 最差的情况
__global__ void random_read(float *input, float *output, int *indices) {
    int idx = threadIdx.x + blockIdx.x * blockDim.x;
    output[idx] = input[indices[idx]];  // 取决于indices的分布
}
```

#### 合并访问图解

考虑一个 warp 中的32个线程（lane 0-31）访问全局内存中的 float（4字节）数组：

<strong>完美合并访问</strong>（所有线程访问连续地址）：

```
线程:     T0  T1  T2  T3  ... T31
地址:    A0  A1  A2  A3  ... A31  (连续4字节地址，共128字节)
结果:    单个128字节事务即可服务所有线程
```

<strong>跨步访问</strong>（stride=2）：

```
线程:     T0    T1    T2    T3    ... T31
地址:    A0    A2    A4    A6    ... A62  (间隔8字节，共256字节范围)
结果:    需要更多事务，一半的读取字节被浪费
```

<strong>分散/随机访问</strong>：

```
线程:     T0     T1      T2      T3      ... T31
地址:    A100   A5      A800    A32     ... A7
结果:    最坏情况下每个线程需要独立的事务
```

#### 各代架构的合并访问行为

不同 Compute Capability 的设备处理全局内存访问的方式略有不同（细节参见 GPU 编程指南中的 Global Memory 章节）：

- <strong>CC 3.x</strong>：支持 L1 和 L2 缓存。128字节的 L1 缓存行意味着合并访问粒度为128字节。
- <strong>CC 5.x / 6.x</strong>：L1 缓存仅用于局部内存，全局内存加载仅缓存在 L2 中（32字节粒度）。提供只读数据缓存（通过 `__ldg()` 使用）。
- <strong>CC 7.x / 8.x</strong>：L1 和共享内存使用同一片上存储，可在每个内核调用时配置划分比例。支持128字节的统一 L1/纹理缓存和32字节的 L2 缓存粒度。
- <strong>CC 9.0 / 10.0 / 12.0</strong>：进一步改进缓存层次结构，支持更大的 L2 缓存和更高效的合并访问。

#### 最大化合并访问的方法

1. <strong>遵循最优访问模式</strong>——让相邻的线程访问相邻的内存地址
2. <strong>使用满足大小和对齐要求的数据类型</strong>
3. <strong>在必要时对数据填充（Padding）</strong>——特别是在访问二维数组时

### 10.4.2 大小和对齐要求（Size and Alignment Requirement）

全局内存指令支持读取或写入大小为1、2、4、8或16字节的字。对全局内存中数据的任何访问（通过变量或指针）<strong>当且仅当</strong>数据类型的大小为1、2、4、8或16字节且数据自然对齐（即其地址是该大小的倍数）时，才编译为单个全局内存指令。

如果不满足此大小和对齐要求，访问将编译为多个具有交错访问模式的指令，这些指令无法完全合并。因此，<strong>强烈建议对驻留在全局内存中的数据使用满足此要求的类型</strong>。

CUDA 内置向量类型（如 `float4`、`int2`、`double2` 等）自动满足对齐要求。

对于结构体，编译器可以使用对齐说明符来强制执行大小和对齐要求：

```cpp
struct __align__(8) {
    float x;
    float y;
};

struct __align__(16) {
    float x;
    float y;
    float z;
};
```

任何驻留在全局内存中的变量地址或由驱动/运行时 API 的内存分配例程返回的地址始终至少对齐到256字节。

> **注意事项**：读取非自然对齐的8字节或16字节字会产生错误结果（偏差几个字），因此必须特别注意维护这些类型的值或数组的起始地址的对齐。

### 10.4.3 二维数组与 Pitched Allocation

一种常见的全局内存访问模式是：索引为 `(tx, ty)` 的每个线程使用以下地址访问宽度为 `width` 的二维数组中的一个元素：

```
BaseAddress + width * ty + tx
```

为了使这些访问完全合并，<strong>线程块的宽度和数组的宽度都必须为 warp 大小（32）的倍数</strong>。

特别是，如果数组的宽度不是 warp 大小的倍数，通过使用向上取整到最接近的 warp 大小倍数的宽度来实际分配数组，并相应地对行进行填充，将显著提高访问效率。`cudaMallocPitch()` 和 `cuMemAllocPitch()` 函数以及相关的内存复制函数使程序员能够编写独立于硬件的代码来分配符合这些约束的数组。

```cpp
// 使用 pitched allocation 分配二维数组
float *d_array;
size_t pitch;  // 实际分配的每行字节数（包含填充）
cudaMallocPitch(&d_array, &pitch, width * sizeof(float), height);

// 在内核中访问
__global__ void process2D(float *array, size_t pitch, int width, int height) {
    int tx = threadIdx.x + blockIdx.x * blockDim.x;
    int ty = threadIdx.y + blockIdx.y * blockDim.y;
    if (tx < width && ty < height) {
        // 使用 pitch 计算行偏移（注意 pitch 是字节数）
        float *row = (float*)((char*)array + ty * pitch);
        row[tx] = /* ... */;
    }
}
```

### 10.4.4 共享内存与 Bank Conflict

共享内存因为是片上内存，比局部或全局内存具有<strong>更高的带宽和更低的延迟</strong>。它是一个强大的用户管理缓存：应用程序显式分配和访问它。典型的编程模式是：

1. 将数据从设备内存加载到共享内存
2. 与块中所有其他线程同步（`__syncthreads()`），使每个线程可以安全地读取由不同线程填充的共享内存位置
3. 处理共享内存中的数据
4. 必要时再次同步以确保共享内存已更新结果
5. 将结果写回设备内存

#### Bank 的组织方式

为了提供高带宽，共享内存被划分为<strong>大小相等的内存模块，称为 Bank（存储体）</strong>。这些 Bank 可以同时访问。如果内存读或写请求的 n 个地址落在 n 个不同的 Bank 中，它们可以<strong>同时被服务</strong>，提供相当于单个模块带宽 n 倍的总体带宽。

然而，如果内存请求的两个地址落在同一个 Bank 中，就产生了 <strong>Bank Conflict（存储体冲突）</strong>，访问必须被<strong>串行化</strong>。硬件将有 Bank Conflict 的内存请求拆分为尽可能多的独立无冲突请求，吞吐量降低的倍数等于独立内存请求的数量。如果独立请求数为 n，则称初始请求引起了 n-way bank conflict。

<strong>对于 Compute Capability 5.x 及以上的设备</strong>，共享内存有32个 Bank，连续的32位字映射到连续的 Bank。每个 Bank 的带宽为每个时钟周期32位。

#### Bank Conflict 示例

```
// 共享内存的 Bank 布局（32-bit 模式）
// 地址:  [0-3]  [4-7]  [8-11] [12-15] ... [124-127]
// Bank:  Bank0  Bank1  Bank2  Bank3   ... Bank31
// 下一层:地址128-131 -> Bank0, 132-135 -> Bank1, ...

// 无 Bank Conflict：
// 32个线程访问 s[threadIdx.x]  → 每个线程访问不同的 Bank

// 2-way Bank Conflict：
// 32个线程访问 s[2 * threadIdx.x]
// thread 0 → Bank0, thread 1 → Bank2, ...
// thread 16 → Bank0 (与thread 0冲突！)
// 需要2次服务

// 32-way Bank Conflict（最坏情况）：
// 32个线程访问 s[32 * threadIdx.x]
// 所有线程访问 Bank0！需要32次服务
```

<strong>常见 Bank Conflict 场景与解决方案</strong>：

```cuda
// 问题场景：共享内存中的二维数组转置
__global__ void transpose_naive(float *odata, float *idata, int width, int height) {
    __shared__ float block[32][33];  // 注意：使用33而非32来避免Bank Conflict
    
    int x = blockIdx.x * 32 + threadIdx.x;
    int y = blockIdx.y * 32 + threadIdx.y;
    
    // 加载（合并的全局读，无Bank Conflict的共享写）
    if (x < width && y < height)
        block[threadIdx.y][threadIdx.x] = idata[y * width + x];
    
    __syncthreads();
    
    // 存储（合并的全局写，无Bank Conflict的共享读）
    x = blockIdx.y * 32 + threadIdx.x;
    y = blockIdx.x * 32 + threadIdx.y;
    if (x < height && y < width)
        odata[y * height + x] = block[threadIdx.x][threadIdx.y];
}
```

<strong>关键技巧</strong>：在共享内存数组声明中<strong>添加一列填充</strong>（如 `block[32][33]` 而非 `block[32][32]`）来避免 Bank Conflict。这一列确保同一列中不同行的元素映射到不同的 Bank。

#### 各代架构的区别

- <strong>CC 3.x</strong>：共享内存有32个 Bank，每个 Bank 4字节宽。支持64位模式（8字节宽的 Bank）。
- <strong>CC 5.x / 6.x / 7.x / 8.x</strong>：共享内存有32个 Bank，每个时钟周期每个 Bank 32位带宽。这些架构也支持64位访问模式，使得 `double` 类型访问无 Bank Conflict。

从 Compute Capability 5.0 开始，当 warp 内线程访问同一 Bank 内的不同地址时，如果所有访问都落在同一 Bank 的同一32位字内，则不会产生 Bank Conflict（这是<strong>广播机制</strong>）。

### 10.4.5 常量内存（Constant Memory）

常量内存空间驻留在设备内存中，并缓存在<strong>常量缓存（Constant Cache）</strong>中。

Warp 对常量内存的请求被拆分为与初始请求中不同内存地址数一样多的独立请求，吞吐量降低的倍数等于独立请求数。然后，如果缓存命中，产生的请求以常量缓存的吞吐量被服务；如果缓存未命中，则以设备内存的吞吐量被服务。

<strong>常量内存的最佳使用场景</strong>：warp 中所有线程读取同一个常量地址。这时只需要一次缓存读取，且这个值被广播到 warp 中的所有线程。这不是推测——这正是常量缓存设计的核心优势。

```cuda
// 常量内存最适合的场景
__constant__ float coeff[256];  // 最多64KB的常量内存

__global__ void apply_filter(float *data, int n) {
    int idx = threadIdx.x + blockIdx.x * blockDim.x;
    if (idx < n) {
        // 当warp中所有线程读取同一coeff[i]时，非常高效
        // 当不同线程读取不同coeff[i]时，性能下降
        float result = 0;
        for (int i = 0; i < 256; i++) {
            result += data[idx + i] * coeff[i];
        }
        data[idx] = result;
    }
}
```

### 10.4.6 局部内存与寄存器溢出（Register Spilling）

局部内存访问只发生在某些自动变量上。编译器可能将以下变量放入局部内存：

- 无法确定使用常量索引访问的数组
- 会消耗过多寄存器空间的大型结构体或数组
- <strong>内核使用的寄存器超过可用数量时的任何变量</strong>——这就是寄存器溢出（Register Spilling）

局部内存空间驻留在设备内存中，因此局部内存访问具有与全局内存访问<strong>相同的高延迟和低带宽</strong>，并受相同的内存合并要求约束。不过，局部内存的组织方式使得连续的32位字由连续的线程 ID 访问。因此，只要 warp 中的所有线程访问相同的相对地址（例如数组变量中的相同索引、结构体变量中的相同成员），访问就是完全合并的。

<strong>如何检测寄存器溢出</strong>：使用 `--ptxas-options=-v` 编译时，编译器报告每个内核的局部内存使用量（`lmem`）。如果 `lmem` > 0，说明发生了寄存器溢出。也可以用 `cuobjdump` 检查 cubin 对象中的指令。

<strong>减少溢出的方法</strong>：
- 使用 `__launch_bounds__()` 限定符提示编译器最优块大小
- 使用 `maxrregcount` 编译器选项限制寄存器数量（但这可能增加溢出）
- 重构代码以减少活跃变量数量

## 10.5 使用 CUDA 事件进行性能测量

CUDA 事件（Event）是进行精确 GPU 内核计时的标准方法。它们在 GPU 时间线上记录时间戳，精度远高于主机端计时。

```cpp
cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);

// 在内核启动前记录
cudaEventRecord(start, 0);  // 在默认流中记录

// 启动内核
myKernel<<<gridSize, blockSize>>>(d_data, N);

// 在内核完成后记录
cudaEventRecord(stop, 0);
cudaEventSynchronize(stop);

// 计算耗时
float milliseconds = 0;
cudaEventElapsedTime(&milliseconds, start, stop);

printf("Kernel execution time: %.3f ms\n", milliseconds);

cudaEventDestroy(start);
cudaEventDestroy(stop);
```

<strong>关键点</strong>：
- `cudaEventRecord()` 将事件放入指定的流中，当流中所有先前的操作完成时才记录
- `cudaEventSynchronize()` 阻塞主机直到事件被记录
- 使用 `cudaEventElapsedTime()` 计算两个事件之间的时间差
- 为了准确测量，应该对多次内核启动进行平均

### 完整的计时模版

```cpp
// 完整的性能测量模版
cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);

const int numIterations = 100;

// 预热（warmup）
myKernel<<<gridSize, blockSize>>>(d_data, N);
cudaDeviceSynchronize();

// 计时迭代
cudaEventRecord(start, 0);
for (int i = 0; i < numIterations; i++) {
    myKernel<<<gridSize, blockSize>>>(d_data, N);
}
cudaEventRecord(stop, 0);
cudaEventSynchronize(stop);

float total_ms = 0;
cudaEventElapsedTime(&total_ms, start, stop);
float avg_ms = total_ms / numIterations;

// 计算带宽或吞吐量
float bandwidth = (N * sizeof(float) * 3) / (avg_ms / 1000.0) / 1e9;  // GB/s
printf("Average time: %.3f ms\n", avg_ms);
printf("Bandwidth: %.2f GB/s\n", bandwidth);

cudaEventDestroy(start);
cudaEventDestroy(stop);
```

## 本章小结

本章涵盖了 CUDA 性能优化的基础——占用率优化和内存访问优化：

1. <strong>性能优化的三大支柱</strong>：最大化利用率（占用率）、最大化内存吞吐量、最大化指令吞吐量
2. <strong>占用率是 GPU 利用率的基石</strong>：它由寄存器使用、共享内存使用和线程块大小共同决定。高占用率意味着更多的 warp 可用于延迟隐藏
3. <strong>全局内存合并访问是性能优化的最高优先级任务</strong>：让相邻线程访问相邻内存地址。非合并访问可使性能降低一个数量级
4. <strong>共享内存是强大的可编程缓存</strong>：但要小心 Bank Conflict——使用填充、改变数据布局等技巧来避免
5. <strong>使用 CUDA 事件进行精确的 GPU 计时</strong>：这是性能优化的度量基础
6. <strong>先测量，再优化</strong>：使用分析器识别瓶颈，针对性地进行优化
