## 17.1 引言

在前面的章节中，我们深入学习了CUDA的各种编程特性和优化技巧。这些特性并非凭空出现——每一项新功能都对应着底层GPU架构的演进。理解GPU架构的演变历程，不仅能帮助你理解为什么某些特性只存在于特定代际的GPU上，还能让你预判未来的技术方向，做出更好的工程决策。

本章将带你纵览NVIDIA GPU架构从Kepler到Blackwell的演变历程，深入分析Hopper和Blackwell两大当代架构的关键特性，并介绍CUDA 12.0+对C++20语言特性的全面支持。

- 了解GPU架构从Kepler（CC 3.x）到Blackwell（CC 10.0/12.0）的演变全景

NVIDIA GPU的架构演进是一个持续近二十年的技术进化故事。每一代架构都在前代基础上引入关键创新，推动计算能力和编程模型的发展。下表汇总了从Kepler到Blackwell的主要架构特性。

### 17.2.2 关键技术创新的代际分布

让我们按照技术主题来梳理这些创新的演进路径：

#### 并行计算基础能力

从Kepler到Pascal，架构优化主要围绕提高SIMT吞吐量展开。Volta引入了<strong>Independent Thread Scheduling（独立线程调度）</strong>，这是自CUDA诞生以来对SIMT模型的最大变革——每个线程拥有自己的程序计数器和调用栈，真正实现了warp内线程的独立执行。

#### Tensor Core的进化

Tensor Core（张量核心）是专门用于矩阵乘加运算的硬件单元，它的出现标志着GPU从通用计算向深度学习加速的重要转向：

- <strong>第1代（Volta, CC 7.0）</strong>：支持fp16输入，fp32累加。基础的 `mma_sync` 操作。
- <strong>第2代（Turing, CC 7.5）</strong>：新增INT8、INT4精度支持，用于推理加速。
- <strong>第3代（Ampere, CC 8.0+）</strong>：新增bf16（Google Brain Float 16）和tf32（TensorFloat-32）支持。tf32使用与fp32相同的范围但只有10位精度，特别适合训练场景。同时引入了稀疏性（sparsity）支持——利用结构化稀疏（2:4模式）使有效吞吐量翻倍。
- <strong>第4代（Hopper, CC 9.0）</strong>：新增FP8支持（E4M3和E5M2两种格式），引入异步MMA指令、warp-group级别的MMA操作、直接从共享内存访问操作数矩阵等高级特性。Hopper还引入了<strong>动态寄存器重分配</strong>能力。
- <strong>第5代（Blackwell, CC 10.0/12.0）</strong>：在Hopper基础上进一步扩展MMA能力。

> NVIDIA官方强烈建议开发者通过CUDA-X库（cuBLAS、cuDNN、cuFFT）或CUTLASS模板库来使用Tensor Core的复杂特性，而非直接编写PTX内联汇编。

#### 内存层次结构的演进

| 代际 | L1/共享内存联合缓存 | 共享内存配置粒度 |
|------|---------------------|-----------------|
| Kepler | 16+48 KB（分开） | 16/32/48 KB |
| Maxwell | 24+64 KB（分开） | 可使用统一内存 |
| Pascal | 24+64 KB（分开） | 同Maxwell |
| Volta | 128 KB（统一） | 最多96 KB（0/8/16/32/64/96 KB） |
| Turing | 96 KB（统一） | 最多64 KB |
| Ampere | 192 KB（统一） | 最多164 KB（10档） |
| Hopper | 256 KB（统一） | 最多228 KB（10档） |
| Blackwell | 256 KB（统一，CC 10.0）<br>100 KB（统一，CC 12.0） | 最多228 KB（CC 10.0）<br>最多100 KB（CC 12.0） |

<strong>关键变化</strong>：

- 从Volta开始，L1缓存和共享内存共享同一物理存储（统一数据缓存），可以根据应用需求灵活配比。
- Ampere及之后架构支持单线程块最多使用超过48 KB的共享内存（称为"大共享内存"），但需要使用<strong>动态共享内存</strong>并显式opt-in。

```cuda
// 在Ampere+上使用大于48KB的共享内存
// 必须使用动态共享内存：
extern __shared__ float bigArray[];

// 必须在主机端设置最大动态共享内存大小：
cudaFuncSetAttribute(myKernel,
                     cudaFuncAttributeMaxDynamicSharedMemorySize,
                     98304);  // 96 KB
```

#### 互联和内存技术的演进

- <strong>Kepler（2012）</strong>：基本的PCIe互联
- <strong>Pascal（2016）</strong>：NVLink 1.0（双向160 GB/s），HBM2显存
- <strong>Volta（2017）</strong>：NVLink 2.0（双向300 GB/s）
- <strong>Ampere（2020）</strong>：NVLink 3.0（双向600 GB/s），MIG（多实例GPU）
- <strong>Hopper（2022）</strong>：NVLink 4.0（双向900 GB/s），NVLink-C2C（Chip-to-Chip互联，用于Grace-Hopper超级芯片），DSM（分布式共享内存）
- <strong>Blackwell（2024）</strong>：NVLink 5.0（双向1.8 TB/s）

## 17.3 深入Hopper架构（CC 9.0）

NVIDIA Hopper架构（以H100 GPU为代表）是CC 9.0的基础，也是目前数据中心GPU的主力架构。它在多个维度上实现了重大突破。

### 17.3.1 SM结构详解

一个Hopper SM由以下单元组成（来自CUDA C++ Programming Guide 13.0）：

- <strong>128个FP32核心</strong>：用于单精度浮点运算。与Ampere的"64+64"（64 FP32 + 64 FP32/INT32）设计不同，Hopper采用了128个专用FP32核心。
- <strong>64个FP64核心</strong>：用于双精度浮点运算（是Ampere的两倍）。
- <strong>64个INT32核心</strong>：用于整数运算。
- <strong>4个第四代混合精度Tensor Core</strong>：支持FP8（E4M3 / E5M2）、fp16、bf16、tf32、INT8和fp64矩阵运算，并支持稀疏性加速。
- <strong>16个特殊功能单元（SFU）</strong>：用于单精度浮点超越函数（sin、cos、exp等）。
- <strong>4个Warp调度器</strong>。

SM将warp静态分配到调度器上。在每个指令发射时刻，每个调度器为其分配的一个已就绪的warp发射一条指令。

### 17.3.2 线程块簇（Thread Block Clusters）

Hopper架构最重要的编程模型创新之一是引入了<strong>Thread Block Clusters</strong>——CUDA层次化编程模型的新层级：

```
Grid → Cluster → Block → Warp → Thread
```

一个Cluster包含最多<strong>8个线程块</strong>（可通过 `cudaOccupancyMaxPotentialClusterSize` 查询是否可以更大）。簇内的线程块被<strong>共同调度</strong>在同一个GPC（Graphics Processing Cluster）上，这意味着它们可以同时驻留并可以直接通过分布式共享内存进行通信。

### 17.3.3 张量内存加速器（TMA）

TMA（Tensor Memory Accelerator）是Hopper引入的专用硬件单元，用于高效地在全局内存和共享内存之间搬运多维数据。它的几大特点包括：

- <strong>多维数据模式</strong>：支持最多5维的张量数据拷贝，自动处理复杂的地址计算。
- <strong>降低寄存器压力</strong>：传统方案需要消耗大量寄存器和指令来做地址计算，TMA将这些工作卸载到专用硬件。
- <strong>多播支持</strong>：在集群场景下，TMA可以将数据同时广播到多个线程块的共享内存中。

### 17.3.4 分布式共享内存（DSM）

DSM允许集群中一个线程块<strong>直接读写</strong>另一个线程块的共享内存。这是跨线程块通信的一次范式转变——此前，块间通信只能通过全局内存进行（使用原子操作或全局同步）。

### 17.3.5 DPX指令集

DPX（Dynamic Programming X）是Hopper引入的一组专门用于<strong>加速动态规划算法</strong>的指令。它提供了：

- 三参数min/max操作（同时比较三个值）
- 带ReLU的min/max操作
- 返回值+选择器（同时返回哪个参数更小/更大）
- 融合的加法+比较操作
- SIMD打包操作（一个32位寄存器打包两个16位操作数）

> "DPX is exceptionally useful when implementing dynamic programming algorithms, such as Smith-Waterman or Needleman-Wunsch in genomics and Floyd-Warshall in route optimization."
> -- CUDA C++ Programming Guide 13.0

DPX在基因组学（Smith-Waterman序列比对算法）和路径规划（Floyd-Warshall算法）等领域具有极高的应用价值。

### 17.3.6 Hopper共享内存配置

Hopper的统一数据缓存总大小为<strong>256 KB</strong>（比Ampere的192 KB增加了1.33倍）。共享内存可以从统一缓存中划分出 0、8、16、32、64、100、132、164、196 或 228 KB。

单线程块最多可寻址<strong>227 KB</strong>共享内存（1 KB保留给系统使用）。当需要超过48 KB共享内存时，必须使用动态共享内存并通过 `cudaFuncSetAttribute` 显式声明。

## 17.4 深入Blackwell架构（CC 10.0 / CC 12.0）

Blackwell是NVIDIA在2024年发布的最新架构，应用于B100/B200等GPU。它继续了Hopper的技术路线，并引入了新的编程模型特性。

### 17.4.1 CC 10.0（数据中心级）

Blackwell CC 10.0的SM结构：

- <strong>128个FP32核心</strong>——与Hopper相同
- <strong>64个FP64核心</strong>——与Hopper相同
- <strong>64个INT32核心</strong>——与Hopper相同
- <strong>4个第五代Tensor Core</strong>——支持FP8（E4M3/E5M2）、fp16、bf16、tf32、INT8、fp64矩阵运算
- <strong>16个特殊功能单元</strong>
- <strong>4个Warp调度器</strong>

统一数据缓存大小为<strong>256 KB</strong>，共享内存配置选项与Hopper相同（0~228 KB，10档）。

### 17.4.2 CC 12.0（消费级Blackwell）

CC 12.0是Blackwell架构的消费级版本。与数据中心版本的关键差异：

- FP32核心：128个（相同）
- <strong>FP64核心：仅2个</strong>（与数据中心版的64个形成鲜明对比——这是消费级定位的体现）
- INT32核心：64个（相同）
- 第五代Tensor Core（相同代数）
- 统一数据缓存：<strong>仅100 KB</strong>
- 最大共享内存/块：<strong>99 KB</strong>
- 共享内存配置：0、8、16、32、64 或 100 KB

<strong>关键洞察</strong>：CC 12.0的设计清楚地展示了NVIDIA对数据中心（CC 10.0）和消费市场（CC 12.0）的差异化策略。消费级GPU大幅削减了FP64计算能力和片上缓存容量，以在更低的成本下为消费者提供最佳的深度学习（通过TC）和游戏体验。

### 17.4.3 Blackwell的新特性：Cluster Launch Control

Cluster Launch Control（集群启动控制）是Blackwell CC 10.0引入的一项独特特性，它支持<strong>工作窃取（work-stealing）</strong>调度策略：

> "Cluster Launch Control allows a kernel to request (cancel) the thread block index of a block that has not yet started execution."
> -- CUDA C++ Programming Guide 13.0

在传统的GPU调度中，有两种常见策略：
1. <strong>固定每块工作量</strong>：SM间负载均衡好，但线程块开销大。
2. <strong>固定线程块数量</strong>：减少块开销，但缺乏负载均衡。

Cluster Launch Control的工作窃取模式提供了第三种选择：一个线程块可以<strong>取消</strong>另一个尚未启动的线程块，并窃取它的工作。这特别适用于变长问题和不规则计算。

### 17.4.4 Hopper vs Blackwell 快速对比

| 方面 | Hopper (CC 9.0) | Blackwell (CC 10.0) | Blackwell (CC 12.0) |
|------|:---:|:---:|:---:|
| 代表产品 | H100 | B100/B200 | 消费级RTX 50系列 |
| Tensor Core代际 | 第4代 | 第5代 | 第5代 |
| FP64能力 | 64核/SM（高性能计算友好） | 64核/SM | 2核/SM（消费级定位） |
| 统一缓存 | 256 KB | 256 KB | 100 KB |
| TMA | 支持 | 支持 | 支持 |
| DSM | 支持 | 支持 | 支持 |
| Cluster Launch Control | 不支持 | 支持 | 需确认 |
| C++20全面支持 | nvcc 12.0+ | nvcc 12.0+ | nvcc 12.0+ |

## 17.5 C++20语言特性在CUDA中的支持

CUDA 12.0（nvcc 12.0）开始全面支持C++20语言特性。但正如CUDA C++一贯的做法，设备代码对这些特性的使用存在一些限制。

> "All C++20 language features are supported in nvcc version 12.0 and later, subject to restrictions described here."
> -- CUDA C++ Programming Guide 13.0

### 17.5.1 C++14/17/20 支持里程碑

| 标准版本 | nvcc版本 | 关键特性 |
|---------|---------|---------|
| C++11 | nvcc 7.0+ | auto、lambda、variadic templates、range-for |
| C++14 | nvcc 8.0+ | 泛型lambda、`decltype(auto)`、relaxed constexpr |
| C++17 | nvcc 11.0+ | `if constexpr`、structured bindings、`std::optional`、fold expressions |
| C++20 | nvcc 12.0+ | 全面支持（有限制），见下文详解 |

### 17.5.2 C++20关键特性及其在CUDA中的使用

#### Lambda表达式（扩展Lambda）

C++20中lambda表达式的能力进一步增强（模板lambda、无状态lambda的默认构造等），这些都在设备代码中得到支持：

```cuda
__global__ void kernel(int *data, int n) {
    // C++20：模板lambda在设备代码中
    auto scale = []<typename T>(T val, T factor) {
        return val * factor;
    };

    int idx = threadIdx.x + blockIdx.x * blockDim.x;
    if (idx < n) {
        data[idx] = scale(data[idx], 2);
    }
}
```

#### constexpr 和 relaxed constexpr

C++20扩展了 `constexpr` 的能力，允许在编译期进行更多操作。在CUDA中，`constexpr` 函数可以在主机和设备代码之间共享：

```cuda
constexpr __host__ __device__ int factorial(int n) {
    int result = 1;
    for (int i = 2; i <= n; i++) {
        result *= i;
    }
    return result;
}

__global__ void useConstexpr(int *data) {
    // factorial在编译期求值
    constexpr int fact10 = factorial(10);
    data[threadIdx.x] = fact10;
}
```

#### 模板和可变参数模板

C++20的concepts约束（`requires` 子句）提供了更清晰的模板接口定义：

```cuda
#include <concepts>

template<typename T>
requires std::is_arithmetic_v<T>
__device__ T myKernelOp(T a, T b) {
    return a * a + b * b;
}
```

#### 三路比较运算符（Spaceship Operator `<=>`）

C++20的三路比较运算符在主机和设备代码中均受支持，但某些使用隐式依赖主机实现的STL功能时可能需要 `--expt-relaxed-constexpr` 标志：

```cuda
#include <compare>

struct Vec3 {
    float x, y, z;
    auto operator<=>(const Vec3& rhs) const = default;
};

__global__ void compareVectors(Vec3 *a, Vec3 *b, int *result) {
    // 使用三路比较运算符
    *result = (*a < *b) ? -1 : ((*b < *a) ? 1 : 0);
}
```

#### consteval 函数

C++20的 `consteval` 关键字在CUDA中有一个特殊用途：允许<strong>跨执行空间调用</strong>。通常，`__device__` 函数不能调用 `__host__` 函数。但 `consteval` 函数突破了这一限制：

```cuda
namespace N1 {
// consteval 主机函数
consteval int hcallee() { return 10; }

__device__ int dfunc() { return hcallee(); /* OK */ }
__global__ void gfunc() { (void)hcallee(); /* OK */ }
__host__ __device__ int hdfunc() { return hcallee();  /* OK */ }
int hfunc() { return hcallee(); /* OK */ }
}

namespace N2 {
// consteval 设备函数
consteval __device__ int dcallee() { return 10; }

__device__ int dfunc() { return dcallee(); /* OK */ }
__global__ void gfunc() { (void)dcallee(); /* OK */ }
__host__ __device__ int hdfunc() { return dcallee();  /* OK */ }
int hfunc() { return dcallee(); /* OK */ }
}
```

### 17.5.3 C++20在CUDA中的限制

C++20中有些特性在CUDA代码中受限或不支持：

#### 模块（Modules）

<strong>不支持</strong>。CUDA C++不支持模块——无论是在主机代码还是设备代码中。使用 `module`、`export` 和 `import` 关键字将被诊断为错误。

#### 协程（Coroutines）

<strong>设备代码中不支持</strong>。在设备函数作用域中使用 `co_await`、`co_yield` 和 `co_return` 关键字将被诊断为错误。

#### `__CUDA_ARCH__` 宏的使用限制

这是一个需要特别注意的限制。以下实体的<strong>类型签名</strong>不能依赖于 `__CUDA_ARCH__` 是否被定义或其值：

- `__global__` 函数和函数模板
- `__device__` 和 `__constant__` 变量
- 纹理和表面

```cuda
// 错误示例
#if !defined(__CUDA_ARCH__)
typedef int mytype;
#else
typedef double mytype;
#endif

__device__ mytype xxx;         // 错误：xxx的类型依赖于__CUDA_ARCH__
__global__ void foo(mytype in,  // 错误：foo的类型依赖于__CUDA_ARCH__
                    mytype *ptr)
{
  *ptr = in;
}
```

此外，如果从主机端实例化并启动一个 `__global__` 函数模板，那么该模板必须在所有编译目标中<strong>使用相同的模板参数</strong>实例化，无论 `__CUDA_ARCH__` 是否定义。

#### 主机编译器扩展

主机编译器特定的语言扩展（如 `__int128` 在部分平台上）在设备代码中的支持有限：

- `__int128` 在受支持的主机编译器下可在设备代码中使用。
- `__float128` 在CC 10.0+设备上受支持。
- `__Complex` 类型仅在主机代码中受支持。

### 17.5.4 编译C++20 CUDA代码

```bash
# 使用nvcc编译C++20 CUDA代码
nvcc -std=c++20 -arch=sm_90 my_cuda_program.cu -o my_program
```

## 17.6 展望未来：CUDA的发展方向

虽然我们无法准确预知NVIDIA的具体产品路线，但基于当前的技术趋势和CUDA编程指南中透露的方向，我们可以做出一些合理的推测。

### 17.6.1 短期趋势（未来1-2年）

1. <strong>C++20工具链成熟化</strong>：nvcc对C++20的支持将持续完善，某些当前受限的特性（如modules的部分支持）可能会逐步开放。

2. <strong>条件图节点的增强</strong>：SWITCH节点在CUDA 12.8才引入，未来可能会看到更多条件控制流的增强（如FOR节点、更强的嵌套能力等）。

3. <strong>异步编程模型的普及</strong>：随着 `cuda::barrier`、`cuda::pipeline` 和TMA等异步机制的成熟，更多的CUDA库和应用将采用异步编程模型。

4. <strong>Cluster Launch Control的应用推广</strong>：随着Blackwell GPU的广泛部署，工作窃取调度策略将逐渐应用于更多不规则计算场景。

### 17.6.2 中期展望（2-5年）

1. <strong>编程模型的进一步简化</strong>：NVIDIA可能会继续降低高级特性（如TMA、DSM）的使用门槛，通过更高级的库和语言扩展来封装复杂性。

2. <strong>AI-native的编程范式</strong>：随着Tensor Core能力和AI工作负载的发展，CUDA可能会引入更多面向AI训练和推理的专用编程抽象。

3. <strong>异构计算的深度融合</strong>：Grace-Hopper和NVLink-C2C预示着CPU-GPU更紧密的耦合，未来可能会出现更统一的CPU-GPU编程模型。

### 17.6.3 值得关注的新兴技术方向

- <strong>FP4 / FP6 等更低精度格式</strong>：随着推理需求增长，更低精度的计算格式可能被添加到Tensor Core支持中。
- <strong>内存池和虚拟内存的进一步发展</strong>：EGM（Extended GPU Memory）和Fabric Memory可能拓展为更通用的跨节点内存管理方案。
- <strong>编译工具的革新</strong>：NVIDIA可能会提供更好的host-device统一编译体验，减少对 `__host__` / `__device__` 注解的依赖性。

   - 是了解API变化的权威来源

## 17.8 本章小结

本章提供了一个从Kepler到Blackwell的GPU架构全景概览。我们首先通过一个综合对比表回顾了八代GPU架构的关键硬件参数和创新特性，然后深入分析了当前最具代表性的两大架构——Hopper（CC 9.0）和Blackwell（CC 10.0/12.0）。

Hopper架构引入了线程块簇（Thread Block Clusters）、张量内存加速器（TMA）、分布式共享内存（DSM）和DPX指令集等关键创新，将GPU编程模型推向了新的高度。Blackwell架构在此基础上继续演进，第五代Tensor Core和Cluster Launch Control等特性进一步拓展了GPU的能力边界。

CC 12.0的发布也展示了NVIDIA对数据中心和消费市场的差异化设计策略——前者强调FP64和缓存容量，后者专注Tensor Core性能和成本效益。

在C++20支持方面，nvcc 12.0+已经全面支持C++20语言特性（modules和coroutines除外），`consteval` 等特性为CUDA代码带来了新的跨执行空间编程可能性。

最后，我们也讨论了如何通过官方文档、Release Notes、GTC和开发者社区等渠道持续跟踪CUDA的发展。在GPU编程这个快速演进的领域，保持学习的习惯至关重要。
